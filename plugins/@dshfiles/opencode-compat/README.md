# OpenCode v2 plugin compatibility

An opt-in Host-only adapter for OpenCode v2 Promise server plugins. It loads configured plugins, reports their status and records calls to unsupported APIs. It is not included in `profiles/web`: loading third-party plugin code into the DSH Host is an explicit user choice, so add the bundle to a profile yourself when you want it. The contract is taken from `@opencode/plugin` 2.2.x (OpenCode MIT, `packages/plugin` checked at commit `67139d6827af`).

## Why a new bundle

1. **Adopt:** no market plugin loads OpenCode plugin modules (the dshmarket index had OpenCode providers, themes and session importers, and nothing that runs a plugin module).
2. **Port:** the OpenCode loader is Bun-first, resolves `effect` and `@opencode/plugin` to the OpenCode host's runtime instances and is wired to OpenCode's own domain services; nothing of it runs against DSH services. OpenCode (MIT) is the spec, not vendored code, so the contract is reimplemented here.
3. **Build:** a Host-only dshx bundle loads the configured modules and hands each one a `Context` whose supported domains call DSH Host services and whose other members are recorded and refused.

## Security

A configured plugin executes arbitrary code inside the DSH Host with the Host user's permissions. Only load code you trust. The agent can inspect status with `opencode_plugins_status` but has no tool to add, enable or change a plugin: allowing that would let the model load arbitrary Host code. Configure the Loader row and settings yourself.

## Settings

Namespace: `dshfiles-opencode-compat`.

| Setting         | Default  | Effect                                                                                                                                                                    |
| --------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `plugins`       | `[]`     | Entries `{ specifier, options, enabled }`; the specifier is an absolute file or directory path, and options is JSON **object text**. Package names are not yet supported. |
| `onUnsupported` | `report` | `report` records calls and returns a no-op registration for registration APIs, or rejects other calls; `fail` throws from the call so uncaught use fails setup.           |

Settings changes dispose loaded plugins and reload the list. Source edits alone do not reload; toggle a setting. Invalid options, duplicate IDs, import and setup errors appear in status with recovery guidance.

## Module contract

A module's default export, or named `server` or `plugin` export, is `{ id: string, setup(ctx) }`. Setup may return an async or synchronous cleanup function. Files and directories with `package.json` exports/main or `index.js` are accepted. Plugin dependencies must resolve from the plugin's own installation; this adapter does not import or vendor OpenCode. `Plugin.define` is the identity function, so a plugin that imports `@opencode/plugin` brings its own copy and still loads. Effect `Schema` values are accepted only from the `effect` instance the Host resolves; a foreign instance is reported as unsupported.

Skill editor reads and mutations cover only skills created by that transform; attempts to update or remove other skills are recorded and ignored. `autoinvoke: false` disables model invocation but leaves user invocation enabled. Storage uses a versioned Host storage domain per plugin ID and the configured Host backend, not the repository. Host `skills`, `systemPrompt` and `storageDomain` services must be available.

The context hook runs on prompt assembly, normally at the first assembly for an agent's stable prompt prefix, not on every turn or context refresh. Each `system` part is one assembled prompt section: editing a part's text, removing, reordering or inserting parts applies to those sections, and tool descriptions can be edited or tools removed. Messages and options edits are recorded as `ctx.session.hook(context).messages` and ignored. When a deployment declares a `complete: true` section, DSH makes it the whole prompt after the waterfall, so system edits have no effect there. Session and agent IDs and the model come from the assembly's agent when present; absent fields are empty strings. Input tool schemas and new tools cannot be changed.

## Unsupported

All other documented context domains and members are unsupported. Calls are recorded by plugin ID and API path with first-seen time and count; **property reads alone are not recorded**. Under `report`, registration-style calls return an idempotent no-op registration; other calls reject with `OpenCodeUnsupportedError`. Under `fail`, unsupported calls throw. Status includes load state, errors, contribution lists and recorded calls.

Every member below exists on the context object, so a plugin never sees a `TypeError`; the call is recorded and follows `onUnsupported`:

1. Provider and model plumbing: `ctx.provider.*`, `ctx.model.*`, `ctx.aisdk.*`, `ctx.credential.*`. DSH routes models through its own LLM adapters and the `ai-accounts` plugin; no AI SDK instance exists to hand out.
2. `ctx.mcp.*`: MCP server config is owned by `@dshfiles/mcp-servers`; a bridge is phase 2 if a real plugin needs it.
3. `ctx.command.*`, `ctx.agent.*`, `ctx.reference.*`, `ctx.integration.*`, `ctx.websearch.*`, `ctx.vcs.*`, `ctx.worktree.*`, `ctx.rpc.*`, `ctx.plugin.list`.
4. Session API verbs (`ctx.session.create`, `prompt`, `synthetic`, `compact`, `interrupt`, …) and every session hook except `context`: `prompt`, `compaction`, `generate`, `title`, `model.request`, `http.request`, `http.response`, `experimental.ws.*`, `retry`, `experimental.idle`. The request itself is built from the Session log and frozen by design, not left as a gap.
5. `ctx.permission.*`, `ctx.shell.hook`, `ctx.location`, `ctx.experimental.*`, `ctx.generate`.
6. TUI and GUI entrypoints (`./tui`, `./gui-experimental`) and the Effect API (`@opencode/plugin/effect`). Only the server entrypoint loads.
7. Hot reload on plugin source change. A settings change reloads; a source change needs a settings toggle.

## Representative plugins

1. The test fixture `tests/fixtures/opencode-sample/index.js` is written to the documented contract, with no adapter imports: an `oc_echo` tool with an Effect `Schema` input, an `execute.before` hook that denies a marker argument, an `execute.after` hook that appends a suffix, one skill, a `context` hook that appends a system line, storage reads and writes, a cleanup function, and one unsupported call (`ctx.mcp.transform`).
2. A copy of the upstream `opencode.figma` plugin (`packages/plugins/figma` with its `skills/`) loads unmodified: its skills register and its `ctx.mcp.transform` is reported. Its skill bodies are replaced with placeholders, because the Figma Developer Terms do not allow redistributing them.

## Verify

From the repository root:

```sh
pnpm --dir plugins/@dshfiles/opencode-compat build
pnpm --dir plugins/@dshfiles/opencode-compat test
pnpm --dir plugins/@dshfiles/opencode-compat typecheck
pnpm --dir plugins run contract
pnpm --dir tooling/dshx run features:check
pnpm check:e2e opencode-compat
```

Host changes require the user's decision to restart the running DSH instance; these checks do not restart it.
