# Phone pairing core

Standalone experimental Node core, enrollment handlers and HTTP proxy test fixture, not a DSH plugin or a deployable gateway. No production listener, UI, or agent tools are provided.

`createPairingCore({ path })` loads a versioned device store. Its parent directory must already exist and be private. Only one core instance/process may own a store at a time. Enrollment and sessions are memory-only and disappear on restart. Device secrets and session secrets are random 256-bit bearer credentials; only their SHA-256 hashes are retained. Revocation persists before returning and invalidates active sessions in this instance. Write failure consumes the enrollment rather than risking duplicate issuance. State is replaced atomically with a mode-0600 file and the parent directory is synced. Storage failures disable authentication until recovery; power-loss behavior remains unverified.

The caller must expose enrollment secrets and device/session credentials only over protected, authenticated channels; never log them or expose them through agent tools. `approveEnrollment` must be reachable only by a trusted authenticated desktop, never by the enrolling phone. The current claim uses the QR bearer alone: anyone who copies it can race the intended phone and redeem after approval. It does not bind the claimant to a device and is unsafe to deploy. A production protocol needs an immutable phone-generated claim, an independently compared confirmation code, atomic approval and redemption of that exact claim, and an authenticated desktop-only approval boundary. Such a code does not defeat compromised endpoints or live relays. Protect the store directory against other local users and symlink manipulation. Transport authentication, brute-force and resource limits, and preventing direct access to the underlying DSH endpoint are not implemented. Fixture origin checks and cookies are not deployment security. Do not deploy until those boundaries are designed and independently verified.

A paired browser has the same DSH privileges as the desktop, including a system-user terminal. A loopback-only approval service can separate direct browser origins, but cannot protect against a paired client intentionally using the terminal or another local process to bypass it. Stronger isolation requires restricted phone capabilities or an independent user-presence authority. Revocation limits future access only if the device has not already established another persistence path.

Run `node --test plugins/@dshfiles/phone-pairing/*.test.mjs` from the repository root. The native bridge test is skipped by default; opt in with `PAIRING_NATIVE_TEST=1 node --test plugins/@dshfiles/phone-pairing/native-bridge.test.mjs`. It boots and removes a disposable DSH host and tests native HTTP and WebSocket framing, not a production deployment.
