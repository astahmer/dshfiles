# Durable remote DSH operations — open release gates

The repository-side lifecycle, [stepwise provisioning and remote administration](../../plugins/@dshfiles/multi-host/README.md#provisioning-and-remote-administration), and verification are documented in the plugin README and [validation record](../../plugins/@dshfiles/multi-host/docs/validation.md). The plugin now supports user-authorized doctor/SSH operations, DSH provisioning steps, headless runtime start/stop/status/logs, and checkout sync. These are operator-invoked operations, not an owner-managed boot service or a pinned release/rollback system. The isolated second-scratch-DSH SSH lifecycle E2E is complete. Physical release acceptance remains open: no target or service owner is selected, and no deployment or live `:3080` restart is in scope. The last recorded host audit is read-only and dated 2026-10-16; treat its access findings as historical, not a fresh reachability check. Do not apply the draft [nixfiles patch](nixfiles-remote-dsh.patch) as-is.

## Open gates

1. **Select one target and service owner.** The last read-only audit (2026-10-16) found the Pi's pinned host key valid but its configured identity denied, and no DSH service or launch metadata in the VPS's registered home; no alternate credentials were tried. These are historical access facts, not a fresh connection test or refusal. Do not infer an owner or ask a broad target-selection question; continue only after the user chooses a specific target, SSH user, `DSH_HOME`, and existing service owner.
2. **Implement the owner-side durable service.** The plugin's headless runtime start is a one-shot `nohup` launch, not a service manager. In the selected owner's repository, pin the official DSH/Node/package-manager/dshfiles/profile/dependency tuple; set `PATH`, `DSHFILES_DIR`, `DSH_HOME`, and loopback bind explicitly; prove profile-sync failure, stop semantics, restart/backoff, and logout/linger behavior. Keep one service owner.
3. **Harden the external supervisor fallback's launch-token boundary.** The plugin-owned `launch.json` already uses private permissions; the open gap is the separate nixfiles `dsh-web` supervisor's `runtime/web-url` fallback. Before accepting it, force private permissions on pre-existing `runtime/` and `web-url`, avoid writing tokenized `dsh web:` output to service logs, and remove stale metadata on every exit path. Verify this fallback on the selected disposable host.
4. **Run disposable Linux release acceptance.** Prove boot/readiness, loopback-only access, wrong host-key/identity rejection, clean stop and crash recovery, pinned upgrade, and rollback while preserving the DSH home, sessions, and runtime identity. State data-migration and backup limits separately.

## Safety boundary

CI and scratch fixtures stay loopback-only and must not contact a real host, mutate the production Swarm, or restart the user's live DSH on `:3080`. Physical service changes remain outside this plan until the user selects the target and owner and a disposable Linux release environment is available.
