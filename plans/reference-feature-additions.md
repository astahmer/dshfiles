## Context

Survey date: 2026-10-05. This is a gap-only software backlog, following the reference survey of T3 Code, OpenCode 2, BB, Codex, Claude Code, Cursor, Pi, Oh My Pi and Amp. Existing functionality has been removed, including native capabilities whose activation still needs validation. Runtime acceptance work belongs to its existing owner, not this additions list.

Evidence: installed DSH 0.2.0-rc.2 declarations and owned plugin source at survey time. Source/registration is not live acceptance; check [`profiles/web/package.json`](../profiles/web/package.json) for the current composition.

Shipped from this list and removed from it (2026-10-14): F05 prompt stash and F06 sent-prompt recall ([`prompt-stash`](../plugins/@dshfiles/prompt-stash/README.md)), F15 viewed files ([`diff-viewed`](../plugins/@dshfiles/diff-viewed/README.md)), F23 workspace per thread ([`jj-integration`](../plugins/@dshfiles/jj-integration/README.md)), F33 and I04 async questions and revisioned feedback ([`agent-questions`](../plugins/@dshfiles/agent-questions/README.md); acceptance left in [async-agent-questions](async-agent-questions.md)), and I10 usage-limit recovery ([`ai-accounts`](../plugins/@dshfiles/ai-accounts/README.md)). F16 (content-digest invalidation) is still open: viewed marks are keyed by session, sequence and path, not content.

Personality prompts and specialist roles are outside scope. A planned feature is not an implemented feature: dedicated plans can still represent real gaps and should be extended rather than duplicated.

### I06 — crash-safe pending work and restart reconciliation

**Separate three concerns.** Conversation recovery restores the transcript and lets a person ask the Agent to continue; it is not replay of the interrupted model/tool call. Durable execution stores a typed operation and execution state so a registered handler can continue or reconcile it. Monitoring reports lifecycle history and output; it does not own or restart the work. Keep each concern with its existing owner unless a tested contract says otherwise.

**Current DSH baseline (stock 0.2.1-rc.2).** Per-Session JSONL logs persist conversation history; the checkpoint policy checkpoints before model requests and top-level tool dispatch. The dshfiles session-controller can resume a stopped turn by submitting a continuation prompt with an idempotent request id; it does not replay the old model/tool invocation. Its prompt explicitly requires checking missing tool results before repeating actions. An interrupted side-effecting tool call therefore has an unknown outcome, not a safe retry. `dsh-jobs-local` runs process-local jobs: an owner/Host exit ends its live execution. Its `JobSpec.run()` callback and live-Agent ownership are not a durable handler registry that can be restored from records. `@dshfiles/background-jobs` indexes registrations/settlements across Sessions and Host processes; an unsettled historical row is `interrupted`, not restarted or reattached, and previous-process output is unavailable. Persistent Agents, durable communication/questions and multi-host Session mirroring provide configuration, messages and remote Session access—not a generic task engine. Each remote Session remains owned by its separate DSH runtime.

**First workflow and boundary.** If the Host gap below is addressed, pilot one user-dispatched, registered Project Checks action, selected only after its configured command is audited and explicitly classified read-only; a `test` or `typecheck` label alone does not prove that. Do not run arbitrary shell or an Agent tool call through this first workflow. Persist a stable task id, source Session/request id, handler kind and version, validated/versioned input, and owner runtime before execution. Pin the exact configured action/version; a missing, disabled or incompatible handler after restart becomes `blocked` for review, never a guessed invocation. Do not transparently replace the current Project Checks path or convert existing jobs. Keep all task records and execution with the owning Host/runtime; remote mirrors may link to that owner but may not run or repair its task. If the initial use case cannot be constrained to read-only work, require an operation-specific provider idempotency key or authoritative status lookup before enabling automatic replay.

**Minimum contract.** Define lifecycle states (`queued`, `running`, `waiting`, `succeeded`, `failed`, `cancelled`, `unknown`, `blocked`), append-only attempt identities linked to the logical task, and durable checkpoints written before each step advances. A handler declares input schema/version, code version or migration, replay classification (`safe`, `idempotent-with-key`, or `unsafe/unknown`), timeout, and reconciliation behavior. Dispatch is idempotent on a caller-supplied key: duplicate admission returns the original task and does not launch a second execution. Record bounded progress and sanitized error/result summaries separately from the source transcript and executor bookkeeping. Cancellation is a persisted request and reaches the running handler's AbortSignal; report `cancelled` only after confirmed stop/compensation, otherwise retain `unknown`/`running` with a visible stop-pending result. Timeout alone is not evidence that an external effect stopped. On boot, a scheduler claims queued/recoverable tasks atomically, inspects each running checkpoint, applies only declared-safe replay, and sends unsafe/incomplete effects to reconciliation; no blind retry. Records remain owned by the workflow store on that Host; corrupt/unreadable storage fails closed and raises operator-visible failure rather than reconstructing work from labels or logs.

**Recovery/replay policy.** A checkpoint separates effect intent, effect result/receipt and the commit that records it. If the process dies after an external effect but before its receipt, classify the outcome unknown and query the provider by the task's stable idempotency key or present it for human reconciliation; do not repeat it merely because the receipt is absent. A handler is replay-safe only when its operation is read-only or the effect boundary proves idempotency; otherwise resume only after reconciliation says not applied or an authorized operator chooses a recovery action. Never claim exactly-once effects without the external system's idempotency/reconciliation guarantee. Conversation continuation remains an explicit new prompt, with the interrupted tool result left unknown for the Agent/human.

**Acceptance gates (fault-inject the handler/store boundary; tests precede any UI).** (1) Kill after persisting intent but before effect: restart recovers once. (2) Kill after effect but before receipt: task becomes `unknown`, reconciles by key/status or requires operator input, and the effect count remains one. (3) Dispatch the same idempotency key concurrently and after restart: one logical task/attempt is admitted. (4) A safe read-only task interrupted mid-step retries from its last checkpoint and settles once; an unsafe task never auto-replays. (5) An unknown provider outcome remains visible and is not labeled failed/succeeded until reconciled. (6) Cancellation before dispatch prevents effects; cancellation during execution signals the handler, and an unconfirmed stop remains visibly pending/unknown. (7) Restart restores queued tasks, checkpoints, attempts, progress and terminal outcomes; missing handler version or corrupt state blocks execution and is surfaced. Also test timeout and stale completion so an old attempt cannot overwrite a newer/reconciled result. The existing acceptance boundary remains: crash between external effect and its receipt must not silently repeat the effect.

**Defer scope unless a chosen workflow proves need.** No general task graphs, child-task ownership/cascade abort, sleeping/wake alarms, fork-aware typed application documents, pluggable storage backends, cross-runtime execution, or multi-human steering in the first increment. Add task dependencies or sleep/wake only for a real workflow requiring parallel children or scheduled waits, with tests for ownership and alarm recovery. The official Pi Durable v1.4.0 design has these broader features, but DSH's persistent agent/configuration/communication and remote-session APIs do not establish those requirements. Keep generic typed/fork-aware documents, backend portability and multi-human collaboration lower priority until a product use case demonstrates them.

## Why

Prioritize recovering past work, preserving drafts, reviewing exact changes and exposing actionable failures. Avoid paying maintenance cost for native features or alternative dashboards that only rearrange existing information.

## How

### Ownership and gates

Adopt a compatible maintained plugin before building. A published peer range permits a scratch-profile probe, not a compatibility claim. Resolve real loader imports, singleton Cordis identity and all required Services, then inspect boot output and browser behavior. Keep experiments out of web.

Host owns sessions, execution, inboxes, permissions and persistence. A plugin cannot implement live workspace transfer, coordinated rewind or provider continuity through UI state alone. dshx exposes verified contracts; add shared helpers only for multiple real callers.
