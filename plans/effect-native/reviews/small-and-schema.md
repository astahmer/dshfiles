### 1.2 Repeated patterns (fix each once)

**P1 — "ctx-bag" services (R2).** `Context.Service<X, { ctx, fs, sessions, … }>` + `Layer.succeed(X, { ctx, … })`: apply-patch/patch-tool.ts:51-66, html-render/host.ts:13-15, goal-stall-guard/host.ts:28-33, request-messages/host.ts:14-30, shared-streams/host.ts:21-36, context-compaction/host.ts:30, rich-composer/host.ts:9-20, model-effort-picker/host.ts:13-20. A service whose shape is "Cordis handles" is not a domain service; it moves `ctx.get` into a Layer and nothing else. Fix: domain services (`PatchFiles.applyEdits`, `PageStore.publish`, `GoalBudget.extend`) built with `Layer.effect(Service, Effect.gen(function* () { const fs = yield* HostFs; … }))`, and one edge layer per Cordis service (see P8).

**P2 — Promise service wrapped whole (R1).** `Layer.succeed(Runtime, createXService(...))` then every handler `Effect.tryPromise(() => runtime.method())`: privacy-controls/host.ts:23,28-38; diff-viewed/marks-host.ts:44-47; loopback-access/host.ts:22-49; plugin-marketplace/host-service.ts:455-466 (`listEffect = tryPromise(() => this.list())`); session-undo/host.ts:158-173; pulls-review/host.ts:69-86. The domain logic never became Effect; delete the wrapper and port the service, or leave it Promise and stop calling it migrated.

**P3 — error flattening (R4).** `message: error instanceof Error ? error.message : String(error)` appears in 16 of 18 migrated units (goal-stall-guard/host.ts:84, goal-continuation.ts:27, request-messages/host.ts:28, shared-streams/host.ts:34,60,73, context-compaction/host.ts:61,92, diff-viewed/marks-host.ts:15, privacy-controls/host.ts:31, rich-composer/host.ts:33, plugin-marketplace/host-service.ts:458,465, workspace-folder-picker/host.ts:36). Repo-wide: **74 `Schema.TaggedError`, 0 `Schema.Defect`**, ≥49 are message-only (`{ message: Schema.String }`). The foundation does it too: every dshx service drops the cause (`catch: () => failed('plugin-storage','get')`, tooling/dshx/packages/dshx/src/effect/services.ts:41-44,61,83-99,153-161,186). apply-patch then rebuilds the lost cause with a `WeakMap` (patch-tool.ts:47,67-71,180-183) — the clearest symptom. Opposite failure: `catch: error => error` (loopback-access/host.ts:28,47; session-undo/host.ts:161,166,171) gives an `unknown` error channel. Fix: `cause: Schema.Defect()` (Schema.ts:9390 — it is a function in 4.1) on every TaggedError, one error per failure kind, and `EffectHostServiceError` gets `cause` + `operation`.

**P4 — `throw` inside Effect code (R4).** `Effect.try({ try: () => { …; throw new Error(...) ×5 } })` (goal-stall-guard/goal-continuation.ts:59-76, :81-95); Layer factory that throws (policies/host.ts:37, workspace-folder-picker/host.ts:44); `throw new ContextCompactionFailure` in a sync callback handed to Promise code (context-compaction/host.ts:76); `try/catch` inside `tryPromise` (pulls-review/host.ts:79-83). Fix: `Effect.gen` + `return yield* new XFailure(...)`; guards become `Effect.filterOrFail`.

**P5 — module-level mutable singletons for settings (R1).** `let settingsScope` + `settings.host({ setup: scope => { settingsScope = scope … } })`: policies/host.ts:13, session-warming/host.ts:15, web-search-brave/host.ts:12; `let opening: Promise` memoised stores: session-undo/host.ts:43, references/host.ts:13-17, agents/host.ts:20; `WeakMap<Context, …>`: context-compaction/host.ts:99, resource-packs/host.ts:9, plus the foundation's own `pluginRuntimes` (tooling/.../effect/index.ts:42). dshx already has `SettingsRead.make(namespace)` (services.ts:178-191) but **no plugin uses it** (0 call sites) because nothing connects `defineSettings(...).host({setup})` to a Layer. Fix in dshx: `DshxEffect.plugin({ settings: policiesSettings, … })` provides `policiesSettings.Tag` (a `SubscriptionRef`-backed service) to the layer; stores open in `Layer.effect` (acquired once per plugin scope — replaces every `opening` memo).

**P6 — listeners outside the Scope (R1/R5).** `ctx.on(...)` called inside a setup Effect without `acquireRelease`: goal-stall-guard/host.ts:103, html-render/host.ts:35, request-messages/host.ts:37. Cordis disposes them with the ctx, so it works, but lifetimes are split between Cordis and the Effect Scope. goal-stall-guard also registers two tools with no disposer at all (goal-continuation.ts:151-154) while apply-patch/html-render wrap the same call in `acquireRelease`. Fix: one `DshxEffect.on(ctx, event, handler)` scoped helper (acquireRelease around `ctx.on`) and `DshxEffect.registerTool`.

**P7 — `const { hostApi: _hostApi, ...effectPlugin } = DshxEffect.plugin(...)` then `...effectPlugin` into `defineHost` (R10).** apply-patch/host.ts:7, html-render/host.ts:17, goal-stall-guard/host.ts:68; others call `effectPlugin.setup(ctx, …)` from a hand-written `setup` (request-messages/host.ts:46, pulls-review/host.ts:102, shared-streams/host.ts:69-75, context-compaction/host.ts:134-138). `setup: () => Effect.void` in 6 units (privacy-controls:26, model-effort-picker:22, rich-composer:24, pulls-review:92, workspace-folder-picker:95, diff-viewed:40). The API is shaped wrong: `plugin` should return a complete `defineHost` input (`name`, `inject`, `Config`, `apis`, `setup`) so there is nothing to destructure or call by hand.

**P8 — Cordis/`ctx.get` reached from everywhere (R2).** E.g. workspace-folder-picker/host.ts:44-61 builds its own Promise `CommandRunner` over `ctx.subprocess.spawn` while dshx ships `Subprocess.spawnScoped` (services.ts:86-92) — unused. dshx needs edge layers for the services plugins actually use: `HostFs` (ctx.fs), `Sessions`, `Agents`, `Goals`, `Tools`, `Llm`, `WebServer`, `StorageDomain`. One `HostServices.layer(ctx)` per plugin, `ctx.get` nowhere else.

**P9 — tests that grep source (R9).** apply-patch/tests/tool-wiring.test.ts:16,24,29 asserts `toContain('Effect.runPromise(')`, `'DshxEffect.plugin({'`, `'Effect.acquireRelease('` — it locks in the facade and must be deleted with the fix. `@effect/vitest` (`it.effect`/`it.layer`) is the target.

### 1.3 The runPromise-in-tools question — yes, a foundation adapter is missing

Sites (all `defineTool` bodies or callbacks handed to Promise APIs):

- apply-patch/src/patch-tool.ts:119 — `execute: (args, execution) => Effect.runPromise(Effect.provide(Effect.fn(...)()..., DshxEffect.tracerLayer), { signal })`
- html-render/src/html-render-tool.ts:70, html-preview-tool.ts:163, html-screenshot-tool.ts:156 — via a bespoke `HtmlRenderEffectRunner` (effect-runner.ts:3) built in host.ts:21-22
- goal-stall-guard/src/goal-continuation.ts:129,148 (no tracer, no signal)
- tool-search/src/host.ts:246 (per-agent tool, `Effect.provide(tracerLayer)` per call)
- mcp-endpoint/src/mcp-server.ts:37, mcp-route.ts:88 (MCP tool calls / HTTP route — real edges, but same shape)
- shared-streams/src/host.ts:70 (Cordis setup — pointless double wrap)
- request-messages/src/host.ts:35 (runner injected into polyfill)
- context-compaction/src/host.ts:122 (summarize callback via WeakMap)
- (also agent-questions/src/host.ts:72,87, service.ts:483, keyed-effect-lock.ts:18 — outside this scope, same pattern)

Why: dshx API methods with `tool:` already run through `registerEffectHost` (tooling/.../effect/index.ts:103-128) in the plugin `ManagedRuntime` with the call's `AbortSignal`, and `apiTool` derives tool parameters from the method schema (tooling/.../api/host-runtime.ts:230-265, `toToolSchema(publishedJsonSchema(...))`). Raw `defineTool` tools get none of that, so every plugin re-invents: (a) the runner (none of them use the plugin runtime → they close over services/ctx instead of `yield*`), (b) tracer provision, (c) signal plumbing, (d) a hand-written JSON parameter object next to an Effect input schema (apply-patch writes the same contract 3 times), (e) `decodeUnknownSync` inside `Effect.try` to decode args, (f) error-to-throw mapping (apply-patch WeakMap).

Proposed foundation addition (one place, ~60 lines, modelled on opencode `tool/runtime.ts:22-60` + `tool/plugin/edit.ts:262-278`):

```ts
// tooling/dshx/packages/dshx/src/effect/tool.ts
DshxEffect.tool({
  name: 'apply_patch',
  description,
  input: ApplyPatchInput,                 // Effect Schema → parameters via the existing toToolSchema
  output: ApplyPatchOutput,               // optional; encode + JSON Schema
  render: (input, output) => [...],
  readOnly?: true,                        // → isConcurrencySafe
  execute: (input, execution) => Effect<Output, ToolFailure | E, R>,
}) // returns a value the plugin registers with yield* DshxEffect.registerTool(tools, def)  (acquireRelease)
```

Runtime behaviour: decode args once with `Schema.decodeUnknownEffect(input, { onExcessProperty: 'error' })` (Schema.ts:1535) → `ToolInputInvalid`; run in the plugin `ManagedRuntime` captured at registration (so `R` is satisfied by `yield*`, not closures) with `{ signal: execution.signal }`; span `tool <name>`; failures: tagged → `throw new Error(message, { cause })`, defects → rethrow the original. `execution` (agent, callId, emit) is exposed as a `ToolExecution` service so domain code can `yield* ToolExecution` instead of threading it. `registerTool` also covers tool-search's per-agent registration (`agent.ctx.tools`). This deletes: all runPromise sites above except mcp-endpoint's HTTP route, `effect-runner.ts`, `patchFailureSources`, hand JSON parameter objects (apply-patch, goal-continuation, html-render ×3, tool-search, pulls-review), and the source-grep test.

Same gap for Cordis callbacks (request-messages, context-compaction): add `DshxEffect.runtime(ctx)`-free `DshxEffect.callback(fn)` = "run this Effect in the current plugin runtime" so the polyfill/engine subclass gets a Promise function without a WeakMap.

### 1.4 Target design (template for every small Host)

```
Cordis edge (defineHost)                        DshxEffect.plugin({ name, inject, Config, settings, layer, setup, apis, tools })
  └─ HostServices.layer(ctx)  ── only place calling ctx.get ──► HostFs | Sessions | Agents | Goals | Tools | Llm | Storage | SettingsRead<NS>
        ▲ Layer.provide
  Domain services (Layer.effect, make = Effect.gen + yield*):   e.g. PatchFiles, PageStore, GoalBudget, ViewedMarks, UndoHistory
        ▲ Layer.provide
  hostApi handlers / DshxEffect.tool executes / scoped listeners (DshxEffect.on)
```

Error taxonomy per plugin: one `Schema.TaggedError` per failure kind with `cause: Schema.optional(Schema.Defect())`; foundation errors: `EffectHostServiceError{service,operation,cause}`, `ToolInputInvalid{issues}`, `PublishEventError{cause}`.

Before/after (apply-patch, the most important change):

```ts
// before (patch-tool.ts:118-190): closure over services, runPromise, decodeUnknownSync in Effect.try, WeakMap cause
execute: (args, execution) => Effect.runPromise(Effect.provide(Effect.fn('apply patch')(function* () {
  const input = yield* Effect.try({ try: () => Schema.decodeUnknownSync(inputSchema, {...})(args), catch: patchFailure })
  ... services.fs.resolve(...)
})().pipe(Effect.catchTag('ApplyPatchFailure', f => patchFailureSources.get(f) ...)), DshxEffect.tracerLayer), { signal })

// after
export const applyPatchTool = DshxEffect.tool({
  name: 'apply_patch', description, input: ApplyPatchInput, output: ApplyPatchOutput, render,
  execute: Effect.fn('apply patch')(function* (input) {
    const files = yield* PatchFiles
    return yield* files.apply(input)       // PatchFiles yields HostFs / Sessions / WorkingDirectory in its make
  }),
})
// host.ts
export default DshxEffect.plugin({ name: '@dshfiles/apply-patch', inject: [...], layer: PatchFiles.layer, tools: [applyPatchTool] })
```
