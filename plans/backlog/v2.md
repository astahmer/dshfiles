## Architecture

### Storage

One SQLite file through `@dshfiles/sqlite-store` (WAL, migrations, `BEGIN IMMEDIATE`), owned by the backlog Host:

| Table | Holds |
| --- | --- |
| `ops` | Append-only op log: `op_id` (ULID), `item_id`, `hlc` (wall ms, counter, host id), `origin`, `op` JSON. Source of truth. |
| `items` | Folded item state (cache), indexed by status, project, updated, origin. Rebuildable from `ops`. |
| `aliases` | `alias → item_id`: legacy `1…576` and new short aliases. |
| `attachments` | Metadata; bytes are content-addressed files `files/<sha256[0:2]>/<sha256>` in the plugin data dir. |
| `connections`, `bindings`, `external_refs`, `sync_state` | Multi-source sync (below). |
| `fts` | FTS5 over title, body, comments, tags; ranking stays the existing scorer. |

Op kinds: `create`, `set {field, value}` (LWW register), `add`/`remove {field: tags|links, value}` (add-wins set),
`comment`, `comment-edit`, `comment-delete`, `external-ref`, `delete` (tombstone). Revert = a new `set` with the prior
typed value from the log, never a rewrite. The 200-event cap goes away; the UI condenses instead.

Migration: a one-shot importer turns each JSON item into `create` + `set` ops in its original order and timestamps,
attachments into files; the JSON domains stay untouched as the rollback. Rehearse on a copy of the live files first,
then compare item-by-item (fields, links, comment counts, attachment hashes).

### Ids

- Canonical id: ULID (sortable, unique on any host without coordination).
- Display: `b:` + 4 lowercase Crockford base32 characters with at least one letter (`b:k3f9`), drawn at random at
  creation and fixed for life. The length grows to 5 once a fifth of the 4-character space is used.
- Legacy `b:1…b:576` stay valid as numeric aliases forever, so every existing thread, commit (`Closes b:12`) and
  comment still resolves. Digit-only means legacy, anything with a letter means new, so the two never collide.
- A collision between two hosts that minted the same alias offline (very unlikely at this size) keeps the older
  item's alias; the newer one gets a new alias and a conflict note.

### Authorship and noise

- `origin: user | agent:<sessionId> | system | remote:<bindingId>` on every item and comment, set once and kept
  outside any cap. `owner` stays the human; an agent working on it is the `delegate` (P3).
- Views hide agent-origin items by default: a "Hide agent items" toggle in every view header, persisted per view and
  in the URL. Touching an item yourself (edit, comment, move, pin) promotes it; an agent item that sets `attention`
  shows regardless.
- Item timeline in two lanes: **Conversation** (your comments, agent answers to you, attention requests) and **Work log**
  (agent progress comments, moves, system events), the work log collapsed to one summary line.
- Search: `created:agent`, `created:me`, negation for every operator (`-by:agent`, `-created:agent`, `-kind:note`).
- A binding does not push agent comments to a remote unless its setting says so.

### Sources (multi-provider, multi-account, multi-host later)

- **Connection** (an account, ai-accounts style): `{id, kind, label, credential: secret:ALIAS, baseUrl?, identity}`.
  Several per provider ("Notion – perso", "Notion – work").
- **Binding** (a sync flow): `{id, connectionId, container (repo, team, data_source_id, JQL, folder), scope: global |
  project path, direction: pull | push | two-way, fieldMap with per-field direction and value maps, conflict policy,
  pollEverySec, ownerHostId}`.
- **External refs**: an item may have several, each `{bindingId, key, url, lastSynced snapshot, lastRemoteVersion}`.
- **Provider port**: providers are separate plugins serving one shared `backlog-provider` Host API id, the
  `vcs-provider-port` pattern. Each declares capabilities (read, write, create, delete mode, status model, body format,
  comments, labels, parent, links, change feed, rate limit) and implements `discover`, `pull(cursor)`, `push(patch)`,
  `toCanonical`, `fromCanonical`. Settings UI per provider through a client registry.
- **Engine** (per binding, on its owner host): pull since cursor → three-way diff against `lastSynced` per field →
  apply one-sided changes (remote ones become ops with `origin: remote:<binding>`, local ones a push) → conflict
  policy on two-sided ones with a conflict note → advance. Polling is the baseline (webhooks need public HTTPS);
  ETags for GitHub, `updatedAt` cursors for Linear/Notion. Per-binding concurrency, not one global lock.
- Canonical status is `{category, label}` so lossy providers round-trip (`doing` survives GitHub's open/closed);
  unmapped provider fields live in namespaced `extras`.
- Providers: `linear`, `github` (ported), `files` (one `.md` per item with YAML frontmatter in a repo folder, two-way,
  mtime/hash scan; doubles as export), `sqlite`/JSONL export, then `notion` (markdown endpoints, data sources), then
  `jira` (ADF converter, transition planner).
- **Multi-host (later)**: each host is a pull-only `peer` source answering "ops after cursor" over the multi-host
  channel (needs a backlog method allowlisted in `@dshfiles/multi-host`). Ops are a grow-only set, so any topology
  converges and offline hosts catch up. Only `ownerHostId` runs a binding's external sync. Rejected: leader host (no
  offline writes) and JSONL-in-git as source of truth (Beads left it).

### Shipped digest

A **Shipped** view and `backlog_shipped` tool: items that reached `done` in a period (hour, day, week, month, year,
custom range), grouped by project, with their linked revisions and PRs, a period-over-period count, and an optional
short AI summary per period (cheap model, cached per period, regenerated on demand). Agent-origin items count but
show their badge. Derived from ops, nothing stored but the cached summaries.
