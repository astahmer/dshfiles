# Parent model calls after inbox waits

**Partial — Refs [astahmer/dshfiles#157](https://github.com/astahmer/dshfiles/issues/157).** This is an offline diagnostic for observed timing and cache-write tokens, not a runtime warning or a measure of cost caused by waiting. Audited at `4c0774edaf0995d0639d235e725a1c977622e62f` (stock DSH `0.2.2-rc.2`, pi-ai `1.6.0`). No live Usage/Traces queries, private sessions, model calls, accounts, or delegation were used.

## Wait semantics

In stock `@deepseek-ai/dsh-tool-subagent`, `subagent` and `subagent_fork` dispatch independently managed children; spawn duration and child lifetime are not time the parent was blocked. The `@deepseek-ai/dsh-subagent` manager delivers settlement by injecting or waking the parent, including resuming an idle parent in a later turn. That later turn is outside this diagnostic. Stock `@deepseek-ai/dsh-tool-subagent-control/src/wait-agent.ts` waits for any new next-step input (or timeout/abort), not for a named child. Already-pending input can return immediately; user steering and agent messages can also wake it. Its result exposes only `timedOut`, so even an `ok` span can mean a timeout, not a child completion. Failed or interrupted waits do not qualify for the union. Even an immediate wait can have a positive recorded duration, and a root span includes result-commit overhead; a nested wait can finish before the enclosing code call returns. Native `workflow` can await children in parallel or pipelines inside a long-running wrapper (`@deepseek-ai/dsh-workflow-ptc/src/runtime.ts`); a wrapper duration is not an exclusive child-wait interval.

## Reproduce without a Host or model

After the repository's normal dependency install:

```sh
node --test scripts/parent-cache-wait.test.mjs
```

The [synthetic fixture](../scripts/parent-cache-wait.test.mjs) uses the pinned `traces_get` response schema and telemetry keys. It exercises fractional-ms boundaries, unknown ends, overlapping waits and model attempts, concurrent children, other tools and side calls, missing/zero usage and price, route changes, failures/retries, cross-turn exclusion, and the CLI. It does not simulate provider behavior. The [diagnostic](../scripts/parent-cache-wait.mjs) accepts one already-created, synthetic or sanitized trace (no query/export), at most 2 MiB and 2,048 spans:

```sh
node scripts/parent-cache-wait.mjs parent < trace.json
```

Replace `parent` with the Session identifier in the supplied fixture. The report pairs adjacent **observed normal model attempts** in the same Session and turn, ordered by start. It emits a row only when the interval from the first attempt's end to the next attempt's start fully encloses a positive-duration `wait_agent` span with status `ok`.

- `pairwiseAttemptGapMs` is the interval between those two endpoints, not parent model inactivity. An earlier concurrent attempt or side call may intersect it. `recordedWaitAgentUnionMs` counts overlapping qualifying span intervals once, not time the parent was blocked. Other positive-duration parent tool and chat spans intersecting the half-open gap are listed separately, including wrappers, failed tools and standalone calls without an attempt marker when their Session ID is recorded. Unscoped or missing calls cannot be joined.
- Offset and duration are converted separately back to integer microseconds before comparison, as the [trace detail projection](../plugins/@dshfiles/traces/src/trace-repo.ts#L889-L895) exposes them independently. A zero offset is a valid start. A zero duration is not treated as a known end: the [normalizer](../plugins/@dshfiles/traces/src/otlp/normalize.ts#L177-L182) can synthesize one for an absent or invalid timestamp. Such spans cannot qualify as overlapping intervals, and a normal attempt with unknown end is not skipped to manufacture a gap. Its known start can still bound a preceding pair.
- Child spans and turn totals never supply parent usage. The first observed next attempt still counts if it fails or changes route; equal recorded provider/model does not imply equal cache identity. Only explicitly present next-call write tokens, total list-price USD and catalog ID are shown (`null` when unavailable). An empty report means no qualifying evidence in that trace, not no waiting or no writes. Output names trace/Session/span IDs but does not echo captured content.

## What remains open

- **Show cache-write cost:** safe future scope is the _observed cache-write component of the next call_, with explicit per-call rates (and a breakout if write modes differ) and provenance; otherwise show tokens or unknown. Even that is not an incremental “wait cost.” A new suffix, changed context/tools, compaction, cache routing, and other calls may explain a write. Determining cost attributable to waiting requires a controlled counterfactual with the same eligible rendered prefix, route, cache policy and tool-result content.
- **TTL warning:** no effective per-request cache policy, reusable prefix identity, expiry or classified child-wait outcome is persisted in these inputs. The pinned [AI Accounts idle-cache heuristic](../plugins/@dshfiles/ai-accounts/src/idle-cache-model.ts#L13-L68) and [retention settings](../plugins/@dshfiles/ai-accounts/src/settings.ts#L93-L100) do not establish policy for a past call. They are deliberately not reused. Prospective owned instrumentation could capture the requested retention at the [provider-profile hook](../plugins/@dshfiles/ai-accounts/src/provider-profile.ts#L260-L277) and record inbox signals correlated with the waiting call, without polling. Neither the requested setting nor a coincident inbox event establishes actual provider retention, prefix reuse, or that the signal ended the wait. This audit does not rule out a deliberately scoped prospective risk warning. [Anthropic Messages](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) documents 5-minute and 1-hour modes, [OpenAI API](https://developers.openai.com/api/docs/guides/prompt-caching#cache-lifetime) documents different lifetimes by model and policy (not a Codex subscription guarantee), and [DeepSeek API](https://api-docs.deepseek.com/guides/kv_cache/) describes best-effort disk caching and hit/miss counters. A time threshold is not proof of expiration. An empirical provider TTL check was not possible within this offline scope; a future warning needs trustworthy route/mode metadata and must be phrased as risk, not a known miss.
- **Delegation cost hint:** a deterministic fixture cannot measure whether a prompt changes delegation, solve rate, or spend. No prompt was changed or executed. A separately authorized opt-in A/B would hold task, routes, budget, tool policy and permissions fixed; vary only the parent instruction; repeat the same task set; compare quality, completion/wait behavior and parent/child token buckets; report price sources and missing data. A separate matched-prefix short/long-gap experiment would be needed for a TTL hypothesis. Neither experiment should silently issue extra calls or reuse data from this audit as a baseline.

The [public post](https://x.com/ibragim_bad/status/2117662415965798757) and [updated Hard12 leaderboard](https://ibragim.dev/leaderboard-v2/) motivate the question; their reported figures differ by snapshot/setup. The leaderboard notes estimated off-peak list rates and potentially missing usage for one newer setup. The benchmark is not evidence for DSH-specific savings, a universal TTL, or a universal write/read ratio. Only public documentation was read; no benchmark code was run.
