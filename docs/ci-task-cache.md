# CI task-cache evaluation

**Decision (2026-11-23): keep the current configuration.** Do not enable hosted Turbo Remote Cache or migrate checks to `pnpm pipeline` on the evidence available. The Actions archive is sometimes a real task hit and sometimes just a download. A remote task cache could fix some archive overhead and shard coverage, but cannot reuse a task whose hash changed. The current gate is red, so this is a research baseline, not a measured CI improvement. Refs [#150](https://github.com/astahmer/dshfiles/issues/150).

## What can be reused

At upstream `4c0774ed`, the pins are [Node 24.11.1](../.node-version), [pnpm 12.5.1 and Turbo 2.11.8](../package.json); [CI setup](../.github/actions/setup/action.yml) also pins pnpm 12.5.1. `pnpm check` is a local aggregate; [Required checks](../.github/workflows/check.yml) instead fans out to 14 Ubuntu 24.04 workers and a gate that waits for all of them. The slowest worker plus startup, queueing, and gate overhead determines elapsed time, not the sum of task times.

| Workers                     | Turbo cacheable work                                                                 | Work outside that cache                                                                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `lint` (1)                  | None                                                                                 | Lint and format checks                                                                                                                                 |
| `types` (1)                 | Plugin and dshx typecheck, including prerequisite builds                             | Direct script typecheck, workspace contract and plugin-script `tsc`; the contract can stop the job before Turbo                                        |
| `units` (4)                 | Round-robin package build and test, shared build dependencies                        | Tests explicitly marked `cache: false`                                                                                                                 |
| `dshx` (1)                  | Build, typecheck and `test:evidence`                                                 | Direct tooling tests, explicitly uncached package tests, feature checks and Knip                                                                       |
| `repo` (1)                  | dshx build and its closure                                                           | Cycles, native forks, script tests, web-profile contract, repo checks, Knip and screenshots gate                                                       |
| `boot` (4), `e2e-smoke` (2) | Build closure and generated owner-level Turbo test tasks; shard 0 owns composed boot | Setup, digest calculation, boot-ignore validation or BDD generation; scenario receipts are a separate workspace cache, not part of the Actions archive |

[`scripts/ci/plugin-shard.mjs`](../scripts/ci/plugin-shard.mjs) selects owners. [`scripts/check-browser.mjs`](../scripts/check-browser.mjs) builds first and hashes selected outputs; the [generated browser tasks](../plugins/@dshfiles/workbench/turbo.json) key on those digests, relevant source/fixtures/profile/lockfile and `CI`/`DSHX_TOOL_VERSIONS`, among other inputs. The [root Turbo configuration](../turbo.json) keys builds on package inputs, dependency task hashes and selected global files/env, with additional cross-workspace inputs for setup UI/UI styles. Build outputs include `dist`, `build`, `tsbuildinfo`, and dshx's `runtime-store`; test/typecheck tasks with `outputs: []` can still cache their logs and a successful outcome. A match does not prove undeclared inputs are correctly modeled, or that cross-platform artifacts are safe to share.

- **Dependencies:** `actions/setup-node` restores pnpm's content-addressable store using `node-cache-<OS>-<arch>-pnpm-<lockfile hash>`, not `node_modules`. Frozen install still materializes the workspace. `pnpm fetch` primes dependency content from the lockfile, useful for layering; it does not cache project tasks. pnpm's local side-effects cache can also reuse eligible installed-dependency lifecycle results. The opt-in 12.0-era [remote side-effects proof of concept](https://pnpm.io/blog/releases/12.0) publishes signed dependency builds to pnpr; it does not replace Turbo and was not tested. Playwright and other setup downloads are separate.
- **Actions archive + local Turbo:** the [wrapper](../scripts/turbo.mjs) uses [`TURBO_CACHE_DIR` or the shared local directory](../scripts/turbo-cache.mjs), `~/.cache/dshfiles/turbo` on CI. Actions restores an archive keyed on runner OS, lockfile hash and a coarse hash over `plugins/**`, `tooling/dshx/**`, `scripts/**`, `tsconfig*.json` and `turbo.json`. Fallbacks are OS+lockfile, then OS. Turbo decides individual hits by task hash after extraction. The archive key has no job or shard dimension. GitHub's cache keys are immutable and scoped by key, version and branch; fallback seeks the most recent compatible archive, not a union. Concurrent same-key saves do not merge. Sibling jobs begin independently and do not get each other's new work through this archive.
- **Turbo remote:** same task hashes and artifacts, fetched on demand instead of restoring one archive on every worker. It can preserve different shards' outputs and reuse a sibling's artifact if that task is published before lookup; concurrently starting cache misses can still duplicate work. A hosted read/write path adds request, upload, auth, retention and trust costs. Audit output, source maps and logs, platform/runtime inputs, the fork-PR read/write boundary and artifact verification before considering it; the docs describe optional HMAC verification, not confidentiality. Do not give untrusted PRs a write credential.
- **pnpm pipeline:** [introduced in 12.4](https://pnpm.io/blog/releases/12.4), experimental and local-only at 12.5.1. It runs a frozen install then a selected task graph; `outputs` enables task replay (including logs), `cache: false` opts out. It would require translating and validating the generated browser keys, package overrides, filters/shards, noncacheable checks and build-output restore contract; changing package managers does not fix the present archive race. Signed remote **workspace task** results and support for Turborepo-compatible servers arrived in [12.12](https://pnpm.io/blog/releases/12.12.0), not at the pin. A task cache is not an install-store cache even when both use the same server.

References: [GitHub cache scope and lifecycle](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [Turbo task caching](https://turborepo.dev/docs/crafting-your-repository/caching), [Turbo Remote Cache](https://turborepo.dev/docs/core-concepts/remote-caching), [pnpm pipeline](https://pnpm.io/cli/pipeline), [pnpm fetch](https://pnpm.io/cli/fetch), [pnpm dependency side-effects cache](https://pnpm.io/pnpr/shared-side-effects-cache).

## Public Actions evidence

The [workflow comment](../.github/workflows/check.yml) reports 465–490 s warm and 786 s cold from creation to successful gate after the split. Those are historical figures without raw samples or a matched control in the comment. The newest successful main run returned by `gh run list -w check.yml -b main -s success` was [Nov 12](https://github.com/astahmer/dshfiles/actions/runs/43193410599): **558 s** from creation to green gate, including queue/setup. Its [critical units shard](https://github.com/astahmer/dshfiles/actions/runs/43193410599/job/131098331340) succeeded in 524 s (112 s setup, 390 s shard command; other phases not included in those two values). It restored 2,152,213,751 bytes but hit only 2/57 build tasks (128.550 s) and 1/86 tasks in the test phase (261.372 s). Do not label that run warm just because it restored a large archive.

Use the gate's `completed_at` and the run's `created_at` for elapsed time. No workflow needs to run again to inspect these observations.

## Synthetic cold/warm controls

Five paired repetitions per mode on macOS arm64 (10 logical CPUs) using the installed pinned binaries and Node 24.11.1. The fixture represents shared-build dependencies, file-producing builds and log-only tests. It does **not** represent runner size, the real package count, Playwright, multi-worker contention, archive transfer, hosted network latency or the CI critical path. Wall time is process spawn to exit, including cache writes for cold runs. No subtraction of install or startup overhead from pipeline times.

| Mode                                                                | Cold ms (median; ordered samples) | Warm ms (median; ordered samples) |
| ------------------------------------------------------------------- | --------------------------------- | --------------------------------- |
| Turbo local task cache only                                         | **515**; 650, 515, 549, 496, 505  | **51**; 72, 51, 66, 50, 49        |
| Turbo remote only, loopback                                         | **522**; 567, 492, 546, 522, 521  | **57**; 52, 57, 57, 51, 59        |
| pnpm 12.5.1 local pipeline                                          | **686**; 613, 647, 706, 686, 719  | **267**; 267, 264, 356, 361, 266  |
| Hosted Turbo, pnpm remote pipeline, or pnpr dependency side effects | Not measured                      | Not measured                      |

Reproduction recipe:

1. Use an empty disposable Git worktree with a pnpm workspace, four packages (`shared`, `alpha`, `beta`, `gamma`), no registry dependencies, and `shared: workspace:*` in the three leaves. Pin pnpm 12.5.1, use `pmOnFail: ignore` only inside the fixture with the direct pinned binary, generate the lockfile offline, and track all inputs. Ignore `node_modules`, `dist`, `.turbo`. Use a separate scratch HOME, temp, XDG state/cache/config/data, stores and credentials-free environment. Restrict the whole process tree to loopback (the measurement used a macOS sandbox allowing file writes only in scratch and networking only to/from localhost). Disable Turbo telemetry/update checks; set pnpm offline and do not report pipeline runs.
2. Both graphs use `build` with `dependsOn: ['^build']` and `outputs: ['dist/**']`, and `test` with `dependsOn: ['build']` and `outputs: []`, concurrency 2. Each script calls Node `pbkdf2Sync(packageName, 'fixture', n, 32, 'sha256')`, with `n=350000` build and `n=150000` test. A build writes `dist/payload` (1 MiB, first 8192 32-byte blocks are `sha256(buildResult || decimalBlockIndex)`, remainder zero); leaf builds require the shared file and tests require their own output. Print one fixed execution marker per task. Declare a pnpm pipeline `default: [build, test]`.
3. For each pair time `turbo run build test --concurrency=2 --output-logs=errors-only` with a fresh cache dir and `--cache=local:rw`; rename that cache before warm replay to model files already restored by Actions, not its download. For loopback set `remoteCache.enabled: true` **only in the fixture**, supply explicit `--api=http://127.0.0.1:<ephemeral port> --team=team_fixture` and a dummy token, and use `--cache=remote:rw` then `--cache=remote:r` with local caching off. The disposable in-memory fixture answers Turbo's artifact status/GET/PUT, starts empty for each pair and is limited to eight 16-hex-hash entries, 1100 KiB per entry and 5 MiB total; no disk persistence or backend. Each pair observed 8 misses, 8 PUTs (1,057,533 B total) and 8 warm GETs. This exercises artifact serialization and restore over loopback, not WAN RTT, hosted authentication, or signature cost.
4. For pnpm, start each pair with a fresh `XDG_CACHE_HOME` and `PNPM_CONFIG_STORE_DIR`; prepare identical no-registry-dependency install state with `pnpm install --offline --frozen-lockfile` before timing `pnpm pipeline --full --offline` twice. This measures task-cold versus task-warm with an equally prepared trivial install, not an install-cold comparison. Delete the generated `dist` directories between invocations without changing inputs. Assert zero hits cold, eight hits warm and identical SHA-256 of all four restored files. Use fresh processes, alternate the order of modes across pairs, and close the fixture and discard scratch artifacts afterwards.

The small warm differences between Turbo transports overlap across samples; there is no evidence of faster hosted hits. The local pipeline demonstrates cache semantics at the current pin, not migration parity or faster CI.

## Revisit after the gate is green

First measure whether archive transfer, shard coverage, or invalidation is on the green critical path. Compare a job-scoped Actions key (with bounded per-lane fallbacks and archive sizes) against the current shared key before taking on a hosted service: per-lane keys could reduce the save race and irrelevant downloads, but can duplicate common artifacts and consume more storage. Do not assume they help until measured. For a separately authorized hosted evaluation, use the same revision, runner class and shard selection, hold install-store state fixed, explicitly empty or preseed task caches, and collect multiple successful runs for each mode. Report creation-to-green, setup/download/save, task hit counts and critical job timing separately. Include a realistic changed-input run, not only all-hit replays. Keep the existing config unless the green-gate result improves without weakening fork-PR checks or introducing unacceptable artifact exposure.
