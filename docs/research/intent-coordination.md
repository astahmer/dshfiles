# Intent coordination review

**Decision (2026-11-23):** Keep the DSH backlog → thread → subagent workflow. Propose one Backlog change: carry the saved plan and acceptance criteria into the thread's first turn. Reuse the existing tickets for agent controls and fleet triage; do not file a workspace-migration or native-mobile request from this comparison alone. This is the research handoff for [astahmer/dshfiles #192](https://github.com/astahmer/dshfiles/issues/192), not an implementation or publication.

## What we could see

- **Demonstrated, not operated:** In the [official recording](https://raw.githubusercontent.com/intent-hq/intent/main/docs/assets/readme/demo.gif), sampled at 0, 3, 6 and 9 seconds, the “Show merge queue position” Spec sits beside the Developer chat with a goal and mock-up; the next view shows a list of delegated agents and a task/agent/machine table, including a Mac Studio and E2B. The [device picker clip](https://intentapp.dev/_astro/features_devices.kPacH5KQ.mp4) shows selectable machines. The [mobile clip](https://intentapp.dev/_astro/features_mobile.Dgv-VNSt.mp4) shows the workspace launcher and device connections with QR/manual pairing; the [mobile showcase](https://intentapp.dev/mobile) illustrates status, questions and chat. These are vendor-selected views, not proof of isolation, transfer integrity, notification delivery or latency.
- **Documented:** The [Spec and Task Notes manual](https://intentapp.dev/docs#context) says the workspace Spec is an autosaved Markdown note for goals, tasks, acceptance criteria and non-goals; `@@@task` blocks become linked Task Notes with assignment, status and optional dependency/conflict attributes. Its [specialist workflow](https://intentapp.dev/docs#agent-specialists) describes a Product Manager drafting, a second reviewing, the user approving, and a Developer dispatching work. The [chat controls](https://intentapp.dev/docs#agents-chat) describe queueing or interrupting a busy agent, answering questions and stopping work. [Workspace transfer](https://intentapp.dev/docs#multi-device-support) stops active agents before copying notes, conversations, assets and the repository (including a work-in-progress snapshot); it may restart agents on the destination, but running processes, terminal sessions, event history and server settings do not move. The [mobile manual](https://intentapp.dev/docs#intent-mobile) describes a paired iOS remote client with questions, queue editing, read-only cached content when disconnected, and completion notifications. None of those behaviors were independently exercised.
- **Access limit:** No hosted, read-only guest workspace was found via the public site, manual or [official repository](https://github.com/intent-hq/intent). The advertised [web option](https://intentapp.dev/docs/remote#web) is self-hosted and requires a generated sign-in key, not a public sandbox. The desktop route requires installation and a provider to run agents; iOS requires a paired machine. Public source/metadata and demonstration media were read only. No sign-in, trial, provider/model calls, scripts from Intent, pairing, repos or project writes. The public [`intent-hq/intent` repository](https://github.com/intent-hq/intent/blob/main/LICENSE) is Apache-2.0; its [README](https://github.com/intent-hq/intent#how-it-works) identifies the iOS source as private. Compute/provider access is separate. The [vendor network disclosure](https://github.com/intent-hq/intent#network--privacy) distinguishes no product analytics from default-on anonymous update counts and external provider/integration traffic. [Remote pairing](https://intentapp.dev/docs/remote#pairing) uses an access token and certificate fingerprint; the web deployment guide says its machine tokens are stored in plaintext and warns against exposing it publicly. These are vendor claims, not a privacy or security audit.

## Ready to file: Include the saved plan and criteria when starting a backlog thread

**Owner:** `@dshfiles/backlog`. **Problem:** A user can record a plan, approve it, and define “done” on the item, then start a thread whose prepared first-turn brief contains the description, replies and attachments but none of those structured fields. A short ref in the message and [`backlog_get`](../../plugins/@dshfiles/backlog/src/api.ts#L375-L390) let the agent look them up, but it has to do so before the missing decisions can affect its first action. Intent's documented workspace-Spec handoff is the useful idea here; a second planning system is not.

**Reproduce:** Create an item with a plain description, put a distinct sentence only in Plan and another only in Acceptance criteria, approve the plan, and start a thread without manually copying either sentence. The [form's default text](../../plugins/@dshfiles/backlog/src/start-thread.ts#L234-L256) is ref/title/preview. The [Host context builder](../../plugins/@dshfiles/backlog/src/backlog-start-context.ts#L100-L116) emits the body and comments and gathers the attachments. [`ThreadStart`](../../plugins/@dshfiles/backlog/src/thread-start.ts#L190-L204) adds that output to the opening message and [queues it](../../plugins/@dshfiles/backlog/src/thread-start.ts#L254-L269). A model-free test reproduced the omission with the real store and builder: the stored approved plan and unchecked criterion round-tripped, the description was present, both unique strings were absent from the prepared launch content. This was not a browser or model run.

**Expected result:**

1. The shared Host path used by the panel and `backlog_start_thread` includes each selected item's nonempty plan and acceptance checklist with check states, in selection order. The approval label comes only from the stored approval field; pending and absent both mean not approved, even if the plan text says otherwise. This is a launch snapshot, not a new approval policy or a gate on turn execution. Later edits remain available via the item ref; they do not trigger a reprompt or dispatch.
2. **Keep generated context inert.** The [default-on lifecycle listener](../../plugins/@dshfiles/backlog/src/settings.ts#L38-L42) [scans user-message text](../../plugins/@dshfiles/backlog/src/lifecycle-signals.ts#L134-L155) and can link a mentioned item and move it to `doing`. The launch path queues generated text in that opening message. Keep a Host-enforced distinction between generated context and user-authored input: automatic mention writes may use deliberate user input, never context copied from the item, including a generated preview, description, reply, plan or criterion. Selected items keep their [explicit start links](../../plugins/@dshfiles/backlog/src/thread-start.ts#L275-L299). A model-facing warning or Markdown delimiter alone cannot enforce this boundary.
3. Keep the existing untrusted-data warning, [100,000-character aggregate context budget](../../plugins/@dshfiles/backlog/src/backlog-start-context.ts#L10-L12) and attachment limits. Refuse an oversized start before queueing a partial prompt. Offer separate starts for a combined selection; if a single item alone is too large, identify its ref and tell the user to shorten its stored context or split the work into smaller backlog items. Do not silently omit criteria or tell a user with one item to split their selection.
4. **Acceptance test (model-free):** Drive the shared Host start against a scratch store and Session fixture that dispatches the actual `user/message` event through the lifecycle listener with default settings. Select two items; reference a third `todo` item only in a selected item's saved plan/checklist. Verify the first queued prompt retains the plan, checklist, descriptions, replies, attachments and selection order. Assert both selected items link to the new thread and the unselected item keeps its status, links and history unchanged after the listener runs. Send a genuine user follow-up deliberately naming that third item; verify the same listener now links it and moves it to `doing`. Cover approved, pending and unset metadata, and check both aggregate and single-item overflow refusals. A formatter-only test or a mock that never emits the event cannot prove the boundary.
