# Workbench slot and panel inventory

M0 evidence snapshot: **2026-10-26**, stock DSH **0.2.1-rc.2**, installed Dockview **8.5.1**. This inventory preserves the pre-implementation/live-native baseline; it is not an after-deployment claim. No core, profile, dependency, or plan changes were needed for that audit.

Implementation follow-up: the [Workbench](../plugins/@dshfiles/workbench/README.md) now has authorized frame and Settings/Sidebar assembly sources, semantic tabs, scoped nested layouts and real resource panels. The [Sidebar Right fork](../plugins/@dshfiles/sidebar-right/README.md) fulfills WB-RESOURCE-01 without a core patch; foreign child render authorization and owner-prop constraints remain. Current schemas and behavior are documented by those owners; the baseline key/shape table below is historical, not a description of the new named/nested layout format.

## Evidence and authorization boundary

- Repository declarations below were read in this worktree. Live read-only inspection used an already-open GUI (private endpoint/profile omitted): `window.__DSH_BOOT__.entries`, mounted `[data-slot]` attributes, the public workbench registry's `list()`, localStorage **key names only**, and authenticated GETs of the boot manifest's served client bundles. No navigation, settings write, restart, or live layout mutation.
- The inspected live profile dependencies pointed at a canonical checkout, **not this worktree**. Its private manifest path is omitted. A source declaration is not proof that its package is active. Boot entries confirmed the distinctions below.
- `dshx inspect slots --json` could not produce an official ledger here: this fresh worktree has no built CLI; the canonical CLI against the repository root returns `DSHX4006` (no entry), and against canonical workbench returns `DSHX3205` (its default profile did not match the inspected live composition). There is no live DSHX inspect bridge directory under the default home. **Do not call this a successful runtime ledger query.** The boot/served-bundle evidence is the bounded alternative; conditional registrations and unknown future plugins must be re-inventoried at runtime.
- The SDK's offline slot catalog still describes **0.2.0-rc.2**, not the installed composition: [catalog header](../tooling/dshx/packages/create-dshx/src/slot-capabilities.ts#L1-L5). It is not the authority for M0.
- Installed contract: slots README (`@deepseek-ai/dsh-client-ui-slots/README.md#L28-L48`). A **registration entry**, not merely a package name, exclusively owns rendering of its declared child slots. Its disposer recursively removes those declarations and contributions. A contributor cannot obtain another entry's renderer by enumerating metadata, re-declare the same child, or pass an arbitrary Session id to a Factory occurrence.

Classification:

- **hostable**: an owned declaring entry can supply its real renderer (and necessary owner props/Session binding) to a panel component. This often requires a small change **in that declarer**; it does not mean every slot is already independently exposed.
- **needs-cooperation**: a foreign declarer owns the renderer. Keep its contributions in their current parent assembly; independently hosting that child requires its opt-in panel/Factory registration, or adopting a maintained owned fork and replacing its Loader row.
- **host-gap**: the requested generic capability is not exposed through supported contracts after checking the plugin-owned route. This is a residual gap, not permission to patch core or mirror another plugin's private state.

### Standalone content versus contextual assemblies (M2 implementation follow-up)

The `thread-sidebar` sidebar root now projects four genuine content assemblies into Add panel: **Threads**
(`sidebar.workspaces`, `{wide:true,expandSidebar}`), **Navigation** (live navigation buttons containing the
real `sidebar.panellist` glyph occurrences with `{size,active}`), **Sidebar status** (`sidebar.footer.above`, `{}`),
and **Sidebar actions** (`sidebar.footer.action`, `{wide:true}`). Registrations follow the declaring root's lifetime,
with the original slots still rendered in the sidebar. Settings already projects actual sections/pages from its own
root. These adapters do not grant the workbench generic permission to render arbitrary child slots.

The table's **hostable** category describes declarer capability, not a promise of a context-free standalone panel.
Brand marks, reopen badges, window chrome, floating notices, settings headers/close controls, composer controls,
message/turn nodes, model labels, resource titles/menus and pending-review actions remain in their real parent
assemblies with their actual subject, scope, hook context and owner props. A separate subject-selecting adapter is
required before any becomes an independent panel. Conversation view panels now use a root-declared session child
under an explicitly retained `SessionProvider`, the public `conversation.content` Factory and its local `views`
Component. The original `conversation.session` remains the sole `conversation.view` renderer and supplies its real
view requests/actions. The owned Factory wrapper omits only the composer for this explicit view-panel context.
The old-thread view/reload journey passes without borrowing the current thread. No occurrence-bound renderer,
private hooks, fake owner callbacks or arbitrary Session bindings are inferred from metadata.

## Dockview 8.5.1: nesting and cross-instance answer

Checked the **installed package**, not an unversioned website: manifest (`dockview-core/package.json#L1-L4`), public SerializedDockview (`dockview-core/dist/cjs/dockview/dockviewComponent.d.ts#L102-L114`).

**Nesting is feasible.** A no-product-code Node/JSDOM spike loaded the installed public `createDockview` export, mounted an inner instance in an outer panel's real content element, split two inner panels, serialized both APIs independently and restored the inner JSON. Result: distinct API ids; **2 nested `.dv-dockview` roots**; outer JSON panels = `container`; inner JSON panels = `inner-a`, `inner-b`; inner `fromJSON` restored **2 panels**. APIs and DOM were disposed; no files or live state changed. This proves construction/independent serialization, **not real-pointer nested drag/focus/scroll behavior**.

**Outer JSON does not serialize arbitrary inner Dockviews.** The spike explicitly confirmed outer JSON contains no `inner-a`. Library “nested grids” for floating/popout groups are not automatic serialization of user-mounted inner instances.

Implementation contract for M6:

1. Stable surface identity is a **panel-instance path**, not just a panel type, title, active group, or Dockview's process-local API id. A versioned escaped/encoded path key must distinguish two occurrences at different depths. Use stable instance ids for ancestors so a parent move does not orphan its children, or migrate the path subtree atomically.
2. Maintain a path-indexed registry of live APIs and separate layout records. Restore parents before children; dispose child subscriptions with their owning panel. A named-layout snapshot must capture the entire surface tree, including unmounted stored children, not only the current three root regions.
3. Prevent dropping a container into itself or its descendants. Generalize the current three-value region registry; preserve ownership and source/target identity during transfer.
4. Do not infer a library depth guarantee: no product depth cap is required by the constructor, but memory, DOM, focus and drag behavior bound useful depth. Browser journeys must prove at least inner split, outer→inner, inner→outer, empty target, close/reopen and reload.

**Cross-instance movement is embedder-owned.** Public group/content drag paths call `onUnhandledDragOver`, accept a foreign drop and emit `onDidDrop`; they do not transplant a foreign instance's component automatically. Installed implementation: group/content handling (`dockview-core/dist/package/main.cjs.js#L11447-L11530`). The layout-edge target **rejects `data.viewId !== host.id` before unhandled-drag dispatch**, including empty targets: root target (`dockview-core/dist/package/main.cjs.js#L13753-L13764`).

Existing workbench correctly adds an HTML5 wrapper fallback for empty/edge foreign transfers ([wrapper](../plugins/@dshfiles/workbench/src/workbench-view.tsx#L194-L253)), and recreates a registered target panel then closes other regions ([adoption](../plugins/@dshfiles/workbench/src/client.tsx#L223-L251)). Caveats for extension: current adoption always chooses `within` for a target group, losing a foreign drop's edge direction; it does not carry arbitrary panel parameters or a nested child-layout tree. Existing region identity is only `main | right | bottom` ([registry](../plugins/@dshfiles/workbench/src/dock-regions.ts#L3-L17)). Keep these as explicit M3/M6 work, not library guarantees. Cross-instance transfer may remount a component; `renderer: 'always'` within one Dockview does not by itself preserve a React instance across APIs.
